# ADR-200: Scheduled tasks (Tarefas)

- Status: accepted
- Date: 2026-11-09

## Context

ADR-172 removed the earlier scheduled tasks together with the to-do list and the webhook entry point, because they pulled the product away from sessions, agents and reviewable changes. The owner now wants a smaller version of one idea only: a prompt that starts a conversation by itself, once or on a repeat rule, shown as a calendar. No webhook, no agent tools, no to-do list.

## Decision

- **A task is a prompt plus a rule.** `{ id, title, prompt, projectId, provider, model, effort?, schedule, enabled, lastRun?, nextRun }`, with `schedule` either `{ once: "YYYY-MM-DDTHH:MM" }` or `{ repeat: { kind: daily | weekdays | weekly, time: "HH:MM", weekdays: [0..6] } }` (0 is Monday). Times are the host's local wall-clock time, kept as naive strings. The host also keeps the last 60 runs of each task (`history`) so the calendar can show ✓ and ✗ for the past.
- **Storage follows ADR-114.** `AppData.scheduledPrompts` is one row per task in a new `scheduled_prompts` table (schema version 8), in the same save transaction as projects and review guides. The name is new on purpose: `scheduled_tasks` of ADR-142 was dropped by version 7 and held another shape. Tasks stay out of `load_state` and out of streaming checkpoints; the window reads them with `list_tasks`.
- **Commands** (`scheduled_prompts.rs`, in `commands.list`): `list_tasks`, `save_task`, `delete_task`, `set_task_enabled`, `run_task_now`. Event: `tasks-updated`, sent when a task is saved, deleted, switched or has run.
  - `list_tasks { from?, to? }` answers `{ now, tasks, occurrences }`: the tasks, the host's local "now", and the runs inside the range (`done` or `failed` from the history, `planned` from the rule, at most 120 days). The window does not repeat the schedule maths.
  - `save_task` validates the prompt, the project, the time and the weekdays, refuses a one-time task in the past, and computes `nextRun`. An edit keeps the task's runs.
- **The schedule maths are pure functions** with unit tests: `next_run` (strictly after a moment), `occurrences` (a range) and `claim_due` (what is due, and each task's next run moved past now).
- **The scheduler** wakes every minute (first pass five seconds after start-up), claims the enabled tasks whose `nextRun` has come, and runs each through `launch::launch`, the path delegation uses: a normal, visible conversation in the task's project, with its provider, model and effort, in the project checkout (no new worktree). It records `lastRun` and the history, and persists.
- **Missed runs run once.** The first pass after launch claims every due task, and claiming moves `nextRun` to the first run after now, so a task that was missed for three days runs a single time and never repeats to catch up. A task already starting is skipped.
- **Permissions.** A run starts with the task's approval, `Ask` by default: nobody is there to answer, so anything that needs approval waits in the conversation instead of running unattended.
- **Repeat rules** now also include `monthly` (`repeat.day`, 1 to 31; a shorter month uses its last day, `monthly_next`). A task also carries `approval` (`ask`, `auto`, `full`), the composer's access modes; a missing value is `ask`, so an unattended run still waits for approval unless the owner chose otherwise. A repeat also has an optional first day (`repeat.start`, `YYYY-MM-DD`: `next_run` never goes before it) and a `custom` kind, "every N days or weeks" (`repeat.every` 1 to 30, `repeat.unit` `days` or `weeks`, counted from `repeat.start`; `custom_next`). A task also carries `fast` (Fast mode, for models that have one) and `worktree` (each run works in a new worktree: `Launch.isolated_worktree`); both default to off and are left out of the JSON when off.
- **The window (revised).** "Tarefas" is a page in its own tab, like Pull requests (`TermState.tasks_tab` / `tasks_active` in `shell_terminal.rs`; it pins, restores and closes like the others). The header has the arrows around the period label (`‹ Novembro de 2026 ›`, the week range or the day) at the left and, at the far right, Dia | Semana | Mês with a sliding accent pill and then "+ Nova tarefa"; there is no "Hoje" button (T still goes to today). At the left, 216 px wide, "Minhas tarefas" lists the tasks with an on/off switch each (no mini calendar). Weeks start on Sunday in Portuguese and Monday in English.
  - **Mês** is a full-height grid: today is a filled accent circle, a run is a flat chip (a soft tint of the provider colour, the time a little brighter, the title in normal text, a quiet ✓ or ✗ at the right), and what does not fit shows as "+N mais", which opens the day. How many chips fit comes from the cell height (`month_cap`, `month_split`). **Semana** and **Dia** are an hour grid with a red now line; a run is a flat block, and hovering an empty half hour shows a ghost that opens the modal at that time. A paused task's coming runs are not drawn (`drawn`); its past ones are.
  - **The run popover** shows the rule in words, when, the project with its robot avatar, the model with effort and ⚡, the access and where it runs, the result of the run (✓ or ✗, "Abrir conversa"), Editar, Executar agora ("Executando…" until the host answers), the Ativa switch and Excluir, which asks once more.
- **Keyboard** (when no modal is open): ← and → step a month, week or day; T is today; D, S and M pick Dia, Semana and Mês; N opens a new task. In the modal Esc closes the open list (project or calendar) first, then the modal; Tab walks the fields; ⌘Enter saves.
- **The modal** ("Nova tarefa" / "Editar tarefa") is one column, 820 px wide at most, with a sticky header and footer, numbered steps, labels in a 104 px column and an 8 px rhythm. 1. **O que fazer**: title, prompt and suggestion chips. 2. **Quem e onde**: the project picker (robot avatar, name, path) with Local / Nova worktree; the model, a compact pill like the composer's (mark, name, chevron) that opens the composer's own catalog popover (`Shell::catalog_page` with `ModelTarget::Task`: provider tabs, search, favourites shared with the composer) and writes into the draft; **Esforço**, a required segmented control whose levels come from the model, with nothing preselected and a pink hint until one is picked; "⚡ Rápido" (greyed out with "indisponível neste modelo") next to Acesso. 3. **Quando**: a compact date field that opens a calendar popover (past days off), the time with steppers, presets, Repetir (Não, Todo dia, Dias úteis, Semanal with weekday chips, Mensal, Personalizado "a cada N dias/semanas") and a muted "Próximas" list. The footer has the live sentence ("escolha o esforço" in pink until chosen), Cancelar and Criar tarefa. Clicking a day, or an empty half hour in Semana and Dia, opens it prefilled; editing sends the same `save_task` with the task's id.
- **Validation** (`Sheet::problems`, shown once a save was tried): a prompt is required, an effort is required (when the model offers levels), a weekly repeat needs a weekday, and a one-off time cannot be in the past.
- **Date and form maths are pure and tested** (`month_grid`, `view_days`, `step_anchor`, `period_label`, `slot_default`, `step_clock`, `month_cap`, `rule_matches`, `upcoming`, `Sheet::problems`, `Sheet::of_task`).
- **Popovers of the modal** open below their field, 6 px away and flush left, or above when the window has no room below (`popover_origin`, pure and tested, from the field's measured bounds). The project, date and model lists fade and slide in and out over 160 ms (`Sheet::set_popup`). The prompt wraps inside its field like the composer's text, grows to 220 px and then scrolls.

## Consequences

- The scheduler runs only while Sirus runs (the host is started with the app); a run missed while it was closed happens at the next launch.
- A run's conversation is not linked back to the task except through `lastRun.sessionId`; "Abrir conversa" fails with a message if that conversation was deleted.
- ADR-172 stays accurate for everything else it removed.
