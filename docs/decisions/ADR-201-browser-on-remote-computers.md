# ADR-201: The embedded browser on a remote computer, and tunnels to its localhost

- Status: accepted
- Date: 2026-11-10

## Context

Sirus Native can switch the whole window to another computer (ADR-133): a headless `sirus-host` on a Linux server, paired from Settings → Conexões. The browser lives in the Mac's window (WKWebView, `panel_browser.rs`), and the host forwards agents' `browser_*` tools to a window client (ADR-189). Until now only the local window qualified (`is_local_window`: the token in `native-token` on a loopback connection), so on a server agents had no browser tools and the panel could not reach the dev servers those agents started on the server's `127.0.0.1`.

The owner wants the browser to work on a remote computer as it does on the Mac: the panel shows the server's pages, and agents on the server can drive it.

## Decision

- **Devices say they are Sirus windows.** Pairing (`POST /api/pair`) takes an optional `kind`; Sirus Native sends `"kind": "desktop"` and the host stores it on the device (`Device.kind`, `remote.json`). The phone sends nothing. Windows paired before this change have no kind; they always paired as `"Sirus"` from no page (the phone pairs as `"iPhone · Sirus"`), so a device without a kind, named exactly `Sirus` and with no page origin, counts as a desktop (`desktop_kind`). A renamed old pairing has to pair again. The kind is the owner's own label, not a security boundary: any paired device already holds a token that drives agents on the host.
- **Who may be the browser client** (`browser_bridge::client_kind`, `command_allowed`): the local window may run every local command, as before. A desktop device on a **headless** host (no window listener of its own, `local_port` unset) may run only `register_browser_client`, `unregister_browser_client` and `browser_tool_result`; never the saved-login, computer-use, remote-access or dictation commands. A phone, a page, or a desktop on a host that has its own window may run none. A later registration replaces an earlier one, as before, and a dropped connection unregisters.
- **When agents see the tools.** The MCP child still decides at launch (`WINDOW_ENV`). A headless host now also lists the browser tools when it has a desktop paired (`remote::desktop_client_possible`), so an agent started while the Mac is on another computer still gets them. Called with no client attached, they answer `NO_CLIENT` ("needs Sirus open on a Mac with this computer selected") instead of the Mac-only `NO_WINDOW`.
- **Secrets.** `browser_fill_login` still hands credentials only to the registered client, now possibly a desktop over the authenticated TLS socket, and only the fields filled return to the agent.
- **The window registers on every remote link.** After `ready`, `remote_session` sends `register_browser_client` with a reply nobody reads (`Link::quiet_id`), so a host that refuses (a Mac with its own window) puts no error on screen. Switching computers closes the link, which unregisters. `browser_tool_request` is accepted from this Mac's host always and from the active computer's link while it is active (`event_accepted`); `deliver` stamps the payload's `via` (`local` or `remote`) and `browser_bridge::answer` sends `browser_tool_result` back on that link (`Backend::invoke_remote` for the remote one). The browser panel was already available on a remote computer; only Terminal, Files and Changes are Mac-only.
- **Tunnels to the host's loopback, like `ssh -L`.** A new route `GET /api/tunnel?port=N` on the host (`tunnel.rs`, wired in `remote.rs`) takes the device token as `Authorization: Bearer` (which a page cannot set on a WebSocket), checked without noting the device as seen, requires a desktop device, accepts ports 1024 to 65535 only, connects to `127.0.0.1:N` then `[::1]:N` before upgrading (a closed port answers 502), and pipes binary frames to that connection. At most 64 tunnels are open at once; revoking the device or stopping the server closes its tunnels.
- **On the Mac** (`native-spike/src/tunnel.rs`), `connect_remote` arms the tunnels with the computer's address and token and `disconnect_remote` closes every listener and connection. `browser_tab::load`, the one place a page is loaded (address bar, suggestions, links, agents' `browser_open`/`browser_navigate`), passes the address through `tunnel::route`: an `http(s)://localhost|127.0.0.1|[::1]:PORT` address (port 1024+) on a remote computer opens a listener on this Mac's `127.0.0.1` (and `[::1]` when free) on the **same port** when nothing here answers there, else any free port with the address rewritten. Each accepted connection opens `wss://host/api/tunnel?port=PORT` and is piped with one thread that waits on both sockets with `poll` (the TLS stream reads with a 1 ms timeout, and everything already decrypted is read before waiting again); a quiet tunnel pings every 30 s so proxies keep an idle HMR socket. A rewritten port reads back as the host's in the tab's address and in what agents see (`tunnel::shown`).

## Consequences

- With the same port, cookies, absolute URLs, CORS origins and HMR sockets work as on the server. When the port is taken on the Mac the page runs on another origin; a server that hard-codes its own origin may then misbehave.
- Only addresses loaded through `browser_tab::load` open a tunnel. A link inside a tunnelled page to another loopback port, or a page's own `fetch` to one, reaches the Mac's own port unless that port was opened before.
- Saved logins are the host's (its vault), and the "let the agent sign in?" approval and the "save this login?" offers stay this Mac's events, so `browser_fill_login` on a server waits for an approval the window does not show yet.
- Each tunnelled connection is its own TLS connection to the host; a page with many parallel requests opens several.
- Old desktop pairings renamed by the owner, and pairings from other clients, are not desktops until they pair again.
